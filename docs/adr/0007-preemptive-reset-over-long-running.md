# 长耗时命令执行期间的系统复位是抢占式，但"抢占"必须先进入安全态

长耗时命令执行期间（BUSY）收到系统复位（0x07），从机不再拒绝，而是抢占式执行：先按板卡规范为该命令定义的安全中止序列停止在途动作、使执行器进入安全态，再应答 0x00 并复位。

安全中止序列是这条决定的代价：每条长耗时命令都必须在板卡规范里定义"被复位中止时如何进入安全态"（附录 C 表 10-3 第 14 项）。定义不出安全中止序列的命令，不得实现为长耗时命令——它不是"可以抢占"的动作。

失败路径是明确的：无法安全中止（未定义序列，或中止序列自身失败）时应答 0x20 且**不执行复位**，同时置故障位并上报。中止与复位序列执行期间到达的第二条 0x07 应答 0x11。结果事件不再发送，主机重新握手后必须重新查询状态，不得假设在途命令的结局。

## Considered Options

- **保持原状（应答 0x11，主机先发停止命令再复位）**：已否决。它把恢复的最后手段交给了从机的忙状态判断，且要求主机在异常路径上走两步；主机侧已经卡死或掉协时，第一步永远发不出去。
- **硬复位，不做安全中止**：已否决。医疗设备上"杀掉一个正在放电/加热/加压的过程"本身就是物理事故，抢占不能实现成断电。
- **由板卡逐条命令声明是否可抢占**：已否决。它把同一条协议语义变成每块板各自的方言，主机无法写出通用的恢复流程。

## Consequences

规范需同步修订：§4.4 增加抢占式复位的五步规则；§4.3.1 把 0x07 列入安全抢占类；§5.2.7 的应答码表分出 0x00（中止后受理）、0x11（并发复位）、0x20（无法安全中止）；表 3-4 与表 6-1 的 0x11 含义随之扩展；表 8-1 的保护措施改写；附录 C 表 10-3 增加第 14 项；附录 B 对应条目删除。

测试影响：票据 #8（长耗时命令闭环）需增加三条用例——忙期间 0x07 得到 0x00 且执行器处于安全态、中止后不发送结果事件、无法安全中止时得到 0x20 且不复位。双实例测试（#12）需覆盖"忙期间复位 → 重新握手 → 在途命令不重放也不假设结局"。
