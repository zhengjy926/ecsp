# 0x07 只提出复位请求，不提前清空会话与事务缓存

从机收到系统复位（0x07）后必须先应答再复位（规范 5.2.7）。库不做硬件复位，因此在应答入队后只置位 `ecsp_slave_reset_requested`；真正把会话打回“等待握手”、把事务缓存清空的，是产品排空发送 FIFO 之后执行的那次 MCU 复位——在本库里就是重新初始化上下文。

所以 0x07 的应答入队**不改变** `ready`、`low_power_mode` 与事务缓存。规范 4.2 说的“从机发生软复位后清空缓存”对应的就是那次真正的复位。

窗口内的两条规则：

* **同一事务的重传回放缓存应答**（规范 4.2）。这正是保留会话与缓存的理由。
* **不同事务序号的新 0x07 应答 0x11，不执行并发复位**（规范 5.2.7 的 0x11、4.4 第 5 条）。复位请求已经提出、序列尚未走完，第二条复位不得开始；`reset_requested` 就是“复位序列进行中”的标志。

## 为什么不当时就清

- **清会话会让重传收到 0x10。** 判定顺序（ADR-0002）是会话先于事务缓存。若应答入队时把 `ready` 清零，主机因应答丢失而重传同一 `(0x07, seq)` 时，管线在第 4 步就回 0x10，而不是回放第一次的 0x00。主机无法把 0x10 与“被拒绝”区分开，而 0x07 的验收要求是同一事务连发三次应答逐字节相同。
- **清缓存会让物理动作执行第二次。** 复位处理函数会再跑一遍，等于对“重复复位”这类非幂等动作失去了 4.2 的保护，正是这张票要消灭的事故。

## Considered Options

- **应答入队即清会话与缓存**（#5 的实现）：重传变成 0x10 或二次执行，两条都违反 4.2，否决。
- **把事务缓存判定提到会话判定之前**：违反 ADR-0002 的固定顺序，且会让缓存条目在会话已死时继续回放，否决。
- **让 0x07 像 0x01 一样豁免会话判定**：等于允许未握手的主机复位从机，违反规范 4.1.2，否决。

## Consequences

- 从“应答入队”到“产品真正复位”之间存在一个窗口，期间上下文仍是就绪态、仍会应答别的命令。窗口长度由产品决定（排空 FIFO 后立即复位），库不额外延长它；要阻止业务继续下发，是产品在 `ecsp_slave_reset_requested` 为真后不再推进业务的事，不是库的事。
- 测试用“重新初始化上下文”模拟 MCU 复位：会话回到等待握手、事务缓存为空。
- 心跳（#7）与忙期间抢占复位（#8）都在这个窗口之上实现，不得在 0x07 应答时反过来清会话或缓存。
