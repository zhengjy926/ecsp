# 全非阻塞、事件驱动、零可变全局状态

库内没有等待循环、没有锁、没有线程：从机与主机两侧都由使用方在周期任务里推进，时钟由调用方以毫秒值推入（`uint32_t`，按无符号相减比较，回绕安全），库不调用任何时间源。库内不存在可变全局状态，每个链路一个上下文，同一固件内可以同时存在主机的上下文与从机的上下文（§2.1 允许同一节点在不同链路担任不同角色）。

主机的 API 只有“提交”与“推进”两种调用，事务结果经回调交付。回调一律在推进调用的栈上同步执行；**允许**在回调里提交新请求（内部只入队，不在回调栈里推进状态机），**禁止**在回调里再次推进同一上下文。

## Considered Options

- **阻塞式请求 API**：`request()` 内部轮询等应答，调用方拿返回值。已否决：在从机上会阻塞接收路径，破坏 §7.1 的响应时间；在主机上会使“重发 + 会话重建”的状态机无法被外部观测。
- **句柄轮询式结果交付**（提交返回句柄，应用自己轮询结果）：已否决：与回调方式共用同一状态机，收益为零，却让应用多一层簿记。

## Consequences

中断上下文只做一件事：把收到的字节塞进接收缓冲。状态机永远在主循环（或单个 RTOS 任务）里推进。

“零全局可变状态”是多链路多角色能成立的前提，也让 PС 上的双实例互联仿真不需要任何隔离设施——两个上下文放进同一进程即可。
