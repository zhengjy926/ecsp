# ECSP 参考实现：Tracer-bullet 票据

配套规格：[`ecsp-impl-spec.md`](ecsp-impl-spec.md)。协议正文：[`ecsp-spec.md`](ecsp-spec.md)。架构决定：[`docs/adr/`](../adr/)。

## 切票原则

* 每张票自包含：开工时只读本票 + 规格对应章节 + 票里点名的 ADR，不依赖上一张票的对话上下文。
* 每张票都必须留下"可执行的正确性"：向量或测试，而不只是能编译的代码。
* 阻塞边是硬依赖：`T4` 在 `T3` 关闭前不动手。**T0 必须先做**——否则向量会退化成实现快照（ADR-0001）。

```
T0 ── T1 ── T2 ──┬─ T3 ── T4 ──┬─ T6 ──┐
                 │       └─ T5 ──┘       ├─ T9
                 └─ T7 ── T8 ────────────┘
```

## T0 向量表与本机测试骨架

**为什么**：没有向量，后续每张票都只能自己证明自己对。这张票把规范里的示例帧变成可执行断言，并立起 `ctest` 入口。

**范围**

* `CMakeLists.txt`：C99、`-Wall -Wextra -Werror`（MSVC `/W4 /WX`）、`enable_testing()`；
* `test/vectors/vectors.h`：X-macro 向量表，字段 `{名称, 字节, 来源章节}`；
* `test/unit/vectors.c`：逐条重算 CRC 并断言整帧字节；
* `tools/check-vectors.ps1`：重算每个向量的 CRC；扫描 `ecsp-spec.md` 中写死具体字节的示例帧，列出"规范有、向量无"的遗漏。

**验收**

* 向量覆盖：3.2 CRC 规则（至少 1 组已知答案）、3.4.1.2 请求/应答、5.2.1 握手三帧、5.2.2 版本应答、5.2.5 序列号写入、5.2.6 序列号应答、5.2.10、5.2.14、5.2.16、5.2.17、5.2.18；
* 删掉任意一条向量，`check-vectors.ps1` 能报出对应章节遗漏；
* `cmake --build && ctest` 在本机全绿。

**阻塞**：无

## T1 L1 帧层：字节助手 + CRC + 帧扫描与编码

**为什么**：其余三层全部建立在"一帧能不能被正确切开"上。ADR-0006 把结构体映射禁掉了，这一层是那条决定的落点。

**范围**

* `bytes.h`：`rd_u16le/wr_u16le/rd_u32le/wr_u32le/ecsp_copy_fixed`；
* `crc.h`：CRC16-MODBUS（初值 0xFFFF，反射多项式 0xA001），种子接口支持分片喂入；
* `frame.h`：`ecsp_frame_scan` / `ecsp_frame_encode`，语义见规格第 4 章；
* `test/unit/frame.c`：帧头缺失、长度越界、帧尾错误、CRC 错、半帧续传、载荷为零/最大。

**验收**

* 规格第 4 章的六条解析规则每条至少一个用例，且断言 `consumed` 的值（前移 1 字节 vs 整帧丢弃不能混）；
* 载荷或 CRC 字段内部出现 `0xFA` / `0x0D` 时仍能正确切帧（`version_resp` 向量就是这种构造）；
* `ecsp_frame_encode` 容量不足返回 0 且不写越界；
* 用 T0 的全部向量跑通扫描与重编码往返。

**阻塞**：T0

## T2 L2 通用命令编解码

**为什么**：把"载荷长度/取值校验"从 handler 里摘出来，管线第 5、8 步才有东西可调。

**范围**

* `cmds.h`：0x01~0x12 的字段级编解码；`ecsp_version_t`（7 字节定长）与逐字节比较；
* 事务序号提取 `ecsp_txn_seq(req)`；
* `test/unit/cmds.c`：每个命令的正常载荷 + 长度错 + 取值错。

**验收**

* 每个通用命令：长度不符返回 `ECSP_E_LEN`，取值非法返回 `ECSP_E_VAL`，二者不得混用；
* 版本比较只做逐字节相等，不做数值解析，也不假设 `'\0'` 结尾；
* 0x03/0x05 的 7/12 字节定长字符串不接受结尾 `0x00`。

**阻塞**：T1

## T3 L3 从机处理管线

**为什么**：ADR-0002 规定判定顺序必须只写一遍。这张票交出那条顺序本身，并用一张"多条件同时命中"的测试表把它钉死。

**范围**

* `slave.h` 上下文、`ecsp_slave_init/rx/step`；
* `engine.c`：管线九步（规格第 6 章表），handler 由 `const` 命令表注入；
* 只实现直通命令 0x01、0x02、0x03、0x04、0x05、0x06、0x07、0x0B、0x12，用来验证管线（会话与时序相关的 0x10/0x11 在 T5，长耗时那组在 T6）；
* `test/unit/pipeline.c`：构造同时命中两个条件的帧，断言应答码。

**验收**

* 管线顺序与规格表逐行对应，且每个判定有独立用例；
* 同一帧同时"地址不匹配 + 命令未知" → 静默丢弃（第 2 步先于第 3 步）；
* 同时"未握手 + 长度错" → 0x10（第 4 步先于第 5 步）；
* handler 内重复做上述检查会被测试抓到（构造一个故意重复的假 handler 验证返回值被覆盖）。

**阻塞**：T1、T2

## T4 L3 事务序号缓存

**为什么**：ADR-0004 的两个清空条件不落地，"重传变重放"就会在真机上变成物理事故。

**范围**

* `txn_cache.c`：FIFO，键 `(cmd, seq)`，存应答帧副本；
* 命中即回放，不调用 handler；未命中按新事务执行；
* 清空：软复位 + 每次收到握手请求（0x01）；
* `test/unit/txn_cache.c`。

**验收**

* 同 `(cmd, seq)` 重发两次，handler 只被调用一次，第二次应答字节与第一次完全相同；
* 容量溢出按 FIFO 淘汰最旧条目；
* 握手请求到达后，原本会命中的旧条目变成未命中（ADR-0004 的核心断言）；
* 缓存条目长度不得超过 `ECSP_MAX_FRAME`，超长应答按"不可缓存"处理并记录。

**阻塞**：T3

## T5 L3 会话、握手与心跳

**为什么**：从机在"没握手"和"已握手"两种人格下的行为完全不同，这一层决定主机看到的是 `正常通信` 还是 `未连接`。

**范围**

* `session.c`：等待握手 → 就绪；1 Hz 握手上报；就绪后心跳 0x10；
* 0x11 故障上报的命令表条目与"置故障位即上报"的触发路径；
* `last_send_ms` 在任一主动帧/应答帧发送后刷新（规范 7.2.2）；
* 意外复位判定：就绪后再次收到握手请求 → 停业务、应答 0x00、回就绪（规范 4.1.4）；
* `test/unit/session.c`：用注入时钟推进，断言上报时刻。

**验收**

* 等待握手期间收到非 0x01 命令 → 0x10，且不改变状态；
* 收到握手请求后停止周期上报，`step` 不再发 0x01；
* 1 Hz 上报的抖动在 ±10% 内，用假时钟逐拍断言；
* 已就绪后再次收到握手请求（主机意外复位），从机应答 0x00 并回到就绪，不再恢复周期上报（规范 4.1.4）。

**阻塞**：T3

## T6 L3 长耗时命令与结果事件

**为什么**：规范 4.3 的三段式（受理→执行→事件 + 获取兜底）是最容易实现成"看起来对"的一段。

**范围**

* 忙状态、`T_exec_max` 定时、结果事件上报、获取结果兜底；
* 0x08/0x09/0x0A（自检）、0x0C/0x0D/0x0E（升级）的命令表条目；
* 安全抢占类命令放行（`ECSP_CMD_PREEMPTIVE`）；
* `test/unit/long_running.c`。

**验收**

* 受理应答载荷为 `[RS][T_exec_max]`，拒绝应答不含该字段；
* 事件单发不重传；事件丢失后 `获取结果` 应答 `0x00/0x00`；
* 超过 `T_exec_max` 后 `获取结果` 应答 `0x00/0x11`；
* 忙期间普通动作命令 → 0x11，标 `PREEMPTIVE` 的停止命令 → 受理；
* 中止后结果码为 0x21。

**阻塞**：T4、T5

## T7 L4 主机双轴状态机与握手/版本核对

**为什么**：ADR-0003 把两条轴分开，就是为了让"这台从机现在能不能接业务命令"有一个不抖动的答案。

**范围**

* `link.c`：会话六态 + 事务四态；主动探测 3 次、被动等待、会话建立总时限；
* 版本核对停在 `版本不符`；重发复用事务序号，`attempt` 挂在事务上；
* 掉线判定：连续 3 个心跳周期无有效帧；
* `test/unit/host_link.c`：假链路 + 假时钟。

**验收**

* 每次提交请求，`正常通信` 不因事务进行而改变（这是双轴的核心断言）；
* 三次无应答 → 判定掉线，事务回空闲且回调只触发一次；
* 版本不等 → `版本不符`，此后拒绝下发业务命令；
* 掉线恢复后必须重新握手才算回到 `正常通信`。

**阻塞**：T1、T2

## T8 L4 公共 API：submit / step / 回调

**为什么**：ADR-0005 的"非阻塞、事件驱动、无全局"是使用方唯一能感知到的接口形状。

**范围**

* `api.c`：`ecsp_host_submit/step/rx`、回调派发、重入保护；
* 回调内允许 submit（入队），禁止再次 step（返回 `ECSP_E_REENT`）；
* `test/unit/host_api.c`。

**验收**

* 回调在 `step` 栈上同步执行，且每事务恰好一次；
* 回调里连续 submit 两条，下一步按序发出；
* 回调里调 step 被拒绝，且状态机未被推进；
* 同一进程两个 host 上下文互不干扰（无全局状态的回归测试）。

**阻塞**：T7

## T9 双实例互操作集成测试

**为什么**：单测各层都对，拼起来仍可能错在层间契约上——尤其是"主机的重发节奏 vs 从机的缓存清空"。

**范围**

* `test/integ/two_instance.c`：一个 host + 一个 slave，字节数组虚拟链路；
* 场景：握手 → 版本核对 → 业务命令 → 长耗时 → 事件丢失走兜底 → 掉线 → 重连 → 重连后旧事务序号不命中；
* 链路注入：丢包、延迟、CRC 损坏、半帧分片。

**验收**

* 三个场景全绿，且每个场景断言的是**规范条款**而不只是返回值；
* 注入 50% 丢包时，非幂等动作最多执行一次（用 handler 计数）；
* 从机重启（重置上下文）后，主机重发的旧序号不会拿到上一次运行的应答。

**阻塞**：T6、T8

## 未切票的部分

以下事项明确不在这批票里，避免实现者顺手做掉：

* 0x13~0x2F 的任何命令（附录 B 待评审）；
* 升级数据通道（规范 5.2.12：由产品规范定义）；
* 具体板卡命令（0x30~0xEF）——由使用方的 `const` 命令表注入；
* 构建系统之外的打包、分发、版本号策略。
